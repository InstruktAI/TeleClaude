# web-tui-shell — Implementation Plan

## Atomicity Assessment

**Verdict: Atomic — single work item.**

- **Coherence test passes.** Layout, tabs, tree, keyboard, footer, and modals
  form one behavior — the TUI shell. A layout without the tree is an empty
  shell. A tree without the layout has nowhere to render. Keyboard navigation
  without the tree has nothing to navigate. Splitting creates a half-working
  codebase at every partition.
- **Detail inverts complexity.** The input specifies exact file paths, field
  names, type definitions, keyboard shortcuts, and component structures. The
  approach is fully known — the builder's job is execution, not discovery.
- **Estimated ~1000-1300 lines** of new/modified code. Within single-session
  capacity given the high detail level.
- **Coordination cost of splitting** (inter-todo deps, sequential review
  rounds, state management) exceeds the session-size benefit.

## Test Verification Approach

Two coverage tracks exist in this plan. The builder must understand which applies to each task:

- **Delivered xfail specs** — expected-failure test files already present in the worktree.
  The builder's first action for each spec-covered task is to remove the `it.fails` markers
  and write the implementation that makes the tests pass. These are the concrete GREEN targets
  for T3 (R3 data layer), T5 (R4), and T11 (R13).

- **Builder TDD (no delivered spec)** — no pre-delivered spec file exists. The builder follows
  RED-GREEN-REFACTOR discipline: write the test first, confirm it fails for the right reason
  (missing behavior, not a setup error), write the minimum production code to make it pass,
  then refactor. This track applies to T1 (R12), T2 (R1, R2), T4 (R3 rendering, R14), T6
  (R6, R7), T7 (R5), T8 (R8), T9 (R9, R10), and T10 (R11). The verification sections in
  those tasks describe exactly what each test must assert.

### T3: Session tree data model

**What:** Create a pure utility that transforms a flat `SessionInfo[]` array
into a hierarchical tree: Computer → Project → Session, with AI-to-AI child
nesting.

Grouping logic:

1. Group by `computer` → `ComputerGroup` nodes
2. Within each computer, group by `project_path` → `ProjectGroup` nodes
3. Sessions with null/undefined `project_path` → synthetic project node
4. Sessions whose `initiator_session_id` matches another session's
   `session_id` → nested as children of the parent, removed from the
   flat project-level list
5. Computer and project nodes carry accurate session counts (including
   nested children)

Types should be discriminated unions (e.g., `type: 'computer' | 'project' |
'session'`) for exhaustive pattern matching in renderers.

**Why:** Isolating the data transformation as a pure function makes it testable
without React. The `initiator_session_id` nesting is the trickiest logic —
containing it here prevents complexity from leaking into the render layer.
The grouping order (computer → project → session) mirrors the terminal TUI
hierarchy exactly.

**Changes:**

- `frontend/lib/sessions/tree.ts` — new: `buildSessionTree()` function and
  supporting types (`ComputerGroup`, `ProjectGroup`, `SessionTreeNode`)

**Referenced types (already defined in `frontend/lib/api/types.ts`):**
`SessionInfo` fields used: `session_id`, `computer`, `project_path`,
`initiator_session_id`, `active_agent`, `status`, `title`, `thinking_mode`,
`subdir`, `last_activity`

**Verification (R3 data layer):**

- Expected-failure spec: `frontend/lib/__tests__/session-tree.test.ts`
  (already delivered, 22 test cases covering grouping, nesting, sorting,
  indexing, enrichment, and counts)
- Builder removes `it.fails` markers and implements until all 22 pass

**Satisfies:** R3 (data layer)

### T4: Session tree rendering

**What:** Create the `SessionTree` component that renders the tree from T3
inside the Sessions tab panel.

Per-level rendering:

- **Computer header:** name, online/offline status badge (derive from the
  existing `useComputers()` query hook), total session count
- **Project header:** project name (last segment of `project_path`),
  truncated full path, session count
- **Session row:** index badge (numeric position), agent icon (Brain/
  Sparkles/Code2 matching the pattern in existing `SessionList.tsx`) colored
  via `var(--tc-agent-{agent}-normal)` CSS variable through the existing
  `useAgentColors` hook, thinking mode label, title (or `session_id` prefix
  fallback), subdir slug
- **Session detail lines:** when a session node is expanded, show
  `session_id`, status, `last_activity` timestamp

`Set<string>` of node IDs keyed by pattern: `computer:{name}`,
`project:{computer}:{path}`, `session:{session_id}`. Computer and project
nodes default expanded; session details default collapsed.

Wrap tree content in shadcn ScrollArea for overflow.

**Why:** The tree is the primary interaction surface. CSS custom properties for
agent colors ensure design token compliance (R14) without hardcoded values.
The `useAgentColors` hook already resolves themed vs peaceful mode — reusing
it maintains consistency with the existing chat UI. ScrollArea handles overflow
with many sessions. Expand state is UI-local (not persisted) — it changes
frequently and has no cross-reload value.

### T5: Activity tracker and highlighting

**What:** Create an `ActivityTracker` module that tracks per-session activity
state from `agent_activity` WebSocket events with timeout-based expiry.
Integrate with the session tree for full-row highlighting.

Tracker API (standalone module, not a React hook — for testability):

- `handleEvent(event: AgentActivityEvent)` — record event `type` for the
  `session_id`, reset expiry timeout
- `isActive(sessionId)` → boolean
- `getActivityType(sessionId)` → string | undefined
- `clear(sessionId)` / `clearAll()` — manual cleanup
- Default timeout: 5000ms — session marked inactive after this duration
  with no new events

Integration: a thin React wrapper subscribes to `agent_activity` events via
`useWS().onEvent()` (the `onEvent` method takes a `WsEventType | "*"` and
an `EventHandler` callback, returns a cleanup function — see
`frontend/lib/ws/useWebSocket.ts:22`) and feeds them to the tracker. The
wrapper exposes reactive state (re-renders on activity changes) that
`SessionTree` consumes for highlight rendering. Active sessions receive a
full-row background highlight using `var(--tc-agent-{name}-subtle)` for a
background wash. The highlight is visually distinct from the cursor highlight
(T7).

**Why:** Real-time activity feedback matches the terminal TUI experience.
Timeout-based expiry prevents stale highlights when activity stops. The
tracker is a standalone module so the core logic (timeout management,
per-session state) is testable without React or timers needing to be
simulated in a component test. The `AgentActivityEvent` type is already
defined in `frontend/lib/api/types.ts` with `session_id`, `type`,
`tool_name`, `tool_preview`, `summary`, and `timestamp` fields.

**Changes:**

- `frontend/lib/sessions/activity.ts` — new: `createActivityTracker()`
  factory function
- `frontend/components/tui/SessionTree.tsx` — modify: accept activity state
  prop, apply highlight classes to active session rows

**Verification (R4):**

- Expected-failure spec: `frontend/lib/__tests__/activity-tracker.test.ts`
  (already delivered, 14 test cases covering initial state, event handling,
  timeout expiry, session independence, and clear operations)
- Builder removes `it.fails` markers and implements until all 14 pass
- Builder TDD for integration: in `SessionTree.test.tsx` — add assertion that
  a session row receives a background-color style referencing

**Satisfies:** R4

### T6: Keyboard navigation infrastructure

**What:** Create a keyboard event handler that:

1. Registers on document `keydown` via `useEffect` (cleanup on unmount)
2. Guards against text input/textarea focus — when `document.activeElement`
   is an `<input>`, `<textarea>`, or has `contenteditable`, all shortcut keys
   pass through to the element (R6)
3. Handles **Esc**: close active modal if one is open, or clear current
   selection if no modal is open
4. Handles **number keys 1-4**: switch active tab subject to focus guard (R7)
5. Dispatches context-specific keys to registered action callbacks based on
   the active tab's `ViewContext`

**Key-map changes required (grounding gap):** The current `ViewContext` type
in `frontend/lib/keys/types.ts` is `'global' | 'sessions' | 'preparation' |
'configuration'` — only 3 non-global contexts. The `BINDINGS` array in
`frontend/lib/keys/bindings.ts` only defines tab-switching bindings for keys
`1`, `2`, `3`. To support the 4th tab:

- Add `'monitoring'` to the `ViewContext` union in `frontend/lib/keys/types.ts`
- Add a key `4` binding to `BINDINGS` in `frontend/lib/keys/bindings.ts`:
  `{ key: '4', description: 'Monitoring tab', action: 'switch_to_monitoring', context: 'global' }`

Use `findBinding(key, modifiers, context)` from
`frontend/lib/keys/bindings.ts` to resolve key presses to binding actions.
The existing binding definitions already cover the `sessions` context with
actions like `navigate_up`, `navigate_down`, `new_session`, `kill_session`,
`restart_agent`, `expand_all`, `collapse_all`.

**Why:** The terminal TUI is fully keyboard-driven. The web TUI must match
this while coexisting with text inputs in modals and the chat input. The focus
guard prevents shortcuts from stealing keypresses from form fields — the most
common keyboard UX bug. Using the existing bindings data from `lib/keys/`
avoids duplicating shortcut definitions and guarantees web shortcuts match the
terminal. The 4th ViewContext/binding addition ensures the key-map model
matches the 4-tab UI; without it, pressing `4` would silently fail.

**Changes:**

- `frontend/lib/keys/types.ts` — modify: add `'monitoring'` to `ViewContext`
  union
- `frontend/lib/keys/bindings.ts` — modify: add key `4` global binding for
  `switch_to_monitoring`
- `frontend/hooks/useKeyboardNavigation.ts` — new: custom hook handling
  document keydown with focus guards, Esc logic, tab switching, and
  action-callback dispatch
- `frontend/components/tui/LeftPanel.tsx` — modify: consume the hook, wire
  tab switching and Esc handling

**Verification (R6, R7):**

- Builder TDD: create `frontend/hooks/__tests__/useKeyboardNavigation.test.ts` —
  assert:
  - Keys 1-4 call the tab-switch callback with the corresponding tab value
    when no input element is focused
  - Keys 1-4 do NOT call the tab-switch callback when an `<input>` element
    has focus (simulate via `document.activeElement` mock)
  - Esc calls the modal-close callback when a modal is open
  - Esc calls the clear-selection callback when no modal is open
  - A context-specific key (e.g., `n` in sessions context) calls the
    registered action callback
  - A context-specific key does NOT fire when a `<textarea>` has focus
- Builder TDD: in `frontend/lib/keys/__tests__/bindings.test.ts` — assert
  `findBinding('4', {}, 'global')` resolves to the `switch_to_monitoring`
  action, confirming the new binding was added correctly

**Satisfies:** R6, R7

### T7: Tree keyboard navigation

**What:** Extend the keyboard infrastructure (T6) with tree-specific
navigation that fires only when the Sessions tab is active:

- **Up/Down arrows:** move cursor through flattened visible tree (expanded
  nodes' children are traversable; collapsed children are skipped)
- **Enter:** on session → select and open in right panel (update
  `?sessionId=` URL param); on project header → open new-session modal
  pre-filled with computer and project
- **Left/Right arrows:** collapse/expand current node
- **+/-:** expand/collapse all tree nodes
- **n:** open new-session modal (no pre-fill)
- **R (shift):** restart selected session via the existing
  `POST /api/sessions/[id]/agent-restart` route (at
  `frontend/app/api/sessions/[id]/agent-restart/route.ts`)
- **k:** end selected session (triggers confirm modal from T9). Note: `k` is
  bound to both `navigate_up` (vi-style, hidden) and `kill_session` in the
  sessions context. The builder must resolve this conflict — the existing
  binding data has `k` mapped to two different actions in the same context.
  Recommended resolution: use `k` for kill (matching the requirement R5) and
  rely on `upArrow` for navigation up.

Cursor state: tracked as a node ID, rendered as a visible highlight distinct
from activity highlighting (T5). Create a `useSessionTree` hook that manages:
cursor position, expand/collapse state, and a computed flattened visible node
list derived from tree data + expanded set. The flattened list provides the
traversal order for arrow key navigation. Navigation wraps at boundaries.

**Why:** Keyboard tree navigation is the core TUI pattern. Separating cursor
from selection allows browsing without changing the right panel until Enter.
The flattened visible list ensures arrows only visit nodes the user can see —
matching terminal behavior exactly. The `useSessionTree` hook encapsulates
tree UI state so components stay focused on rendering.

**Changes:**

- `frontend/hooks/useKeyboardNavigation.ts` — modify: add tree action
  dispatch (arrows, Enter, +/-, n, R, k) via action callbacks
- `frontend/hooks/useSessionTree.ts` — new: tree cursor, expand/collapse
  state, visible node flattening
- `frontend/components/tui/SessionTree.tsx` — modify: render cursor
  highlight, accept cursor position from hook

**Verification (R5):**

  - Moving cursor up goes to previous visible node

item currently cursored/selected.

returns `Array<{ key: string; description: string }>` with non-hidden

- Nothing selected: general navigation (arrows, +/-, n)

label in a horizontal wrapping layout. Use design token variables for styling

including global bindings. For the new `monitoring` context (T6), it will
return only the global bindings since no monitoring-specific bindings are
defined — this is correct for a placeholder tab.

**Why:** The terminal TUI footer teaches the interface through context-
sensitive hints. Users learn shortcuts by looking at the footer as they
navigate. Dynamic updates as cursor moves provide the same discoverability.
`getFooterHints()` already returns formatted key/description pairs filtered
by `ViewContext`.

**Changes:**
