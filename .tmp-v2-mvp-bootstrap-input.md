# v2-mvp-bootstrap — Input

## Goal

Build the v2 Rust MVP: a Postgres-backed Rust workflow service, exposed
via a Rust CLI binary, bridged to v1 via Redis events, with v1 cutover
for all `telec todo` and `telec roadmap` commands.

This is the FIRST cutover in the v2 migration. It proves the pattern
(services as crates, Postgres-per-service, Redis event bridge, atomic
cutover) that every subsequent service migration will follow.

## Strict scope

**IN scope (the MVP delivers exactly this):**

- Rust workspace at `crates/` with members per `file-layout.md`
- `crates/shared/` (primitives), `crates/observability/`, `crates/storage/`,
  `crates/event_bus/`, `crates/identity/` (single-user stub),
  `crates/workflow/` (full), `crates/telec-cli/`
- Postgres + Redis via `docker-compose.yml`, `make pg-up`/`pg-down`
- `telec migrate-workflow-v1` data migration command
- v1 daemon Python addition: subscribe to `workflow.*` Redis channels,
  refresh cache, push WebSocket update
- Cutover PR: data migration + v1 path deletions + v1 CLI dispatch
  replacement + Redis bridge wiring

**OUT of scope (do NOT include; surface as separate todos if needed):**

- Rust TUI (`telec-tui` binary). v1 TUI continues.
- Rust daemon (`telec-daemon` binary). v1 Python daemon continues.
- Rust HTTP API (`telec-api` binary). v1 daemon's HTTP API continues.
- `telec-hook` binary. v1 Python hook receiver continues.
- Webhook receivers in Rust. v1 Python webhook handlers continue.
- Other service crates: `agent_runtime`, `session_ledger`, `knowledge`,
  `integration`, `config`, `agent_artifacts`. All stay v1 entirely.
- Full identity service. Only single-user stub in MVP.
- Frontend changes. `frontend/` Next.js untouched.

## Team-mode dispatch instructions (MANDATORY for the build worker)

This todo MUST be executed by the `next-build` worker using Claude Code's
**Team mode primitives** (`TeamCreate`, `Agent` tool with `team_name`,
`SendMessage`, `TaskCreate`/`TaskUpdate`, `TeamDelete`). Spawned teammates
inherit NO context from the parent — each gets only the prompt sent to it.
Therefore every teammate brief must be self-contained.

### Build worker (parent) responsibilities

The `next-build` worker session that lands inside the
`trees/v2-mvp-bootstrap/` worktree is the team lead. It MUST:

1. **Create the team:**
   ```
   TeamCreate({
     team_name: "v2-mvp",
     agent_type: "team-lead",
     description: "v2 MVP build — workflow service + CLI + cutover"
   })
   ```

2. **Translate the DAG into the shared task list.** For each Wave A–I task
   above, call `TaskCreate` with `description` matching the task's
   deliverable and `addBlockedBy` pointing at upstream task IDs. After
   creation, the task list mirrors the DAG.

3. **Per-wave parallel dispatch.** For each wave with parallel tasks,
   spawn ALL teammates for that wave in a SINGLE message (multiple
   `Agent` tool calls in one message run concurrently). Example for
   Wave B:
   ```
   Agent({team_name: "v2-mvp", name: "shared-builder",        subagent_type: "general-purpose", prompt: <B1 brief>})
   Agent({team_name: "v2-mvp", name: "observability-builder", subagent_type: "general-purpose", prompt: <B2 brief>})
   Agent({team_name: "v2-mvp", name: "event-bus-builder",     subagent_type: "general-purpose", prompt: <B3 brief>})
   ```

4. **Use the teammate prompt template** (below) for every spawned
   teammate. Each brief is self-contained.

5. **Wave gating.** After teammates report task completion, run
   integration check (`cargo build --workspace`, `cargo clippy
   --all-targets -- -D warnings`). Only after green: dispatch next wave.
   If red: send corrective `SendMessage` to the responsible teammate;
   they fix and re-mark complete.

6. **Wave I (cutover) is NOT delegated.** The build worker performs
   cutover itself — this is the integration moment, sequential and
   careful. No teammate spawn for Wave I.

7. **Teardown on completion.** When all tasks are complete and the
   cutover smoke tests pass:
   - SendMessage to each teammate with `{type: "shutdown_request"}`
   - After all teammates shut down: `TeamDelete()`

### Parallelism summary

Per the DAG `depends_on` declarations (which are authoritative):

- **Wave A:** 1 worker sequential (build worker does it directly, or 1 teammate)
- **Wave B:** 3 teammates concurrent (B1, B2, B3 — all only depend on A1)
- **Wave C:** 2 teammates concurrent (C1, C2 — both only depend on B1)
- **Wave D:** **3 teammates concurrent initially** (D1, D2, D3 — D1 needs C1; D2 needs B1; D3 needs B1+B3). **Then D4 starts after D2 completes** (D4 needs LifecyclePhase from D2). So Wave D is not "4 all at once" — orchestrator must respect dependencies; D4 launches when D2 reports complete, possibly while D1 and D3 are still running.
- **Wave E:** 1 teammate (composition; needs ALL of Wave D done)
- **Wave F + G + H:** 3 teammates concurrent (F1, G1 depend on E1; H1 only depends on B3 so can actually start much earlier in parallel with C/D/E)
- **Wave I:** build worker direct (no teammate; sequential cutover)

**Optimization:** H1 (v1 Python Redis-bridge addition) only depends on B3
(event_bus crate complete). The orchestrator MAY dispatch H1 as soon as
B3 reports complete — H1 can run in parallel with all of C/D/E/F/G. This
shortens calendar time.

### Time type choice

Use `chrono::DateTime<chrono::Utc>` everywhere. Serde via the workspace's
chrono feature `serde`. Postgres `TIMESTAMPTZ` columns. Never naive
`DateTime<Local>`. Never `std::time::SystemTime` in domain types.

### Important v2 deviations from v1 to encode

- **No DRAFT phase persisted.** v2 initial lifecycle phase is `PrdDrafting`
  when any artifact is present, never `Draft`. The `Draft` enum variant
  exists for backward compatibility with v1 SQLite data during migration
  only; the state machine never returns it post-migration.
- **No `telec todo create` with empty input.** v2 enforces that a todo
  cannot be constructed without an `input` artifact. See redesign-list
  entries #4-#6.
- **Single Redis transport for events** (no in-process LOCAL variant).
- **No `_on_mutation` process-local hook.** Mutations emit Redis events;
  any process that cares subscribes.

1. `cargo build --release --workspace` succeeds without warnings.
2. `cargo test --workspace` passes (unit + integration).

## Anti-patterns to refuse

Per `redesign-list.md`, the worker must NOT:

- Add `unwrap()` / `expect()` / `panic!()` in production paths.
- Add `lazy_static!` or `OnceCell` for service singletons.
- Use `mod.rs` files; use `<name>.rs` at parent level.
- Use leading-underscore filenames for "internal" modules; use Rust
  visibility modifiers instead.
- Reach into other crates' internal modules.
- Add HTTP / gRPC / Unix-socket transports between local Rust processes.
- Add a dual-transport event bus (LOCAL + CLUSTER).
- Add fallback storage for "Redis is down" / "Postgres is down" — fail
  loudly instead.
- Add direct DB queries against another service's schema.
- Dual-write across v1 SQLite and v2 Postgres.
- Call v1 Python from v2 Rust or vice versa (Redis events only).
- Expand MVP scope (add TUI, daemon, hooks, other services, etc.).
