# telec-code-rust-support — Input

## Goal

Add Rust as a first-class language in the `telec code` quality pipeline
so `telec code lint`, `test`, `format`, and `commit` invoke cargo
tooling on Rust code the same way they invoke ruff/pyright on Python and
biome/tsc on TypeScript.

This is v1 Python work. It unblocks the v2 MVP and every subsequent v2
service migration by giving Rust agents the same `telec code` interface
Python agents have today.

## Why now

The v2 MVP exposed the gap: when a teammate runs `telec code lint`
inside a worktree that contains both Python (`teleclaude/`) and Rust
(`crates/`), only the Python steps fire. Rust agents have to call cargo
directly via Bash, which means:

- Pre-commit hooks installed via the `telec code commit` path don't gate
  Rust quality.
- Inconsistent agent experience: Python agents use `telec code`, Rust
  agents use `cargo`. New agents have to know the split.
- Future v2 service migrations re-invent this gap each time.

Fix it once, in v1, before more Rust code lands.

## Scope

**IN scope:**

- Register Rust in the language toolchain (`teleclaude/quality/toolchain.py`)
- Add Rust lint steps to `teleclaude/quality/lint.py`:
  `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings`,
  scoped to changed Rust files (workspace member crates if changes are
  per-crate)
- Add Rust test steps to `teleclaude/quality/test_runner.py`:
  `cargo test` for changed crates (or workspace-wide for `--all`)
- Add Rust format step to `teleclaude/quality/format.py`: `cargo fmt`
  for changed Rust files or the workspace
- Update `teleclaude/quality/scope.py` to recognize Rust workspace
  member crates so changed-file detection maps a touched file to its
  owning crate (for per-crate test/lint scoping)
- Update pre-commit configuration (`.pre-commit-config.yaml`) to invoke
  the language-aware quality pipeline on Rust file changes (or directly
  invoke cargo via pre-commit hooks if that's simpler — the BA decides
  based on existing patterns)
- Documentation:
  - Update `telec-cli.md` docs section for `telec code` if behavior
    documentation lives there
  - Add Rust to any language reference in agent artifacts that lists
    supported languages

**OUT of scope:**

- The v2 Rust workspace itself (lives in `crates/`, separate
  responsibility — built by v2 MVP)
- New quality tools beyond cargo (no rustfmt config beyond defaults
  unless current Python/TS handling sets precedent for opinionated
  configs; if so, mirror that pattern)
- CI configuration changes (separate concern — if CI runs `telec code`
  commands, this todo's changes flow through transparently; if CI
  invokes cargo directly, that's a separate update)

## Pattern to follow

The existing Python and TypeScript handling shows the pattern. Mirror
it:

1. **Registry entry** in `toolchain.py`: register `rust` alongside
   `python` and `typescript`. Tool resolution likely lazy (only when a
   project declares `rust` in its `languages` list).
2. **Per-pipeline-step Rust support** in lint/format/test_runner: check
   `if "rust" in self._languages`, invoke appropriate cargo commands.
3. **Scope module**: extend changed-file detection to recognize
   `crates/<name>/src/**/*.rs` and `crates/<name>/migrations/**/*.sql`
   (sqlx migrations are part of Rust crate scope).
4. **Workspace-aware scoping**: when changed files all live in one
   crate, run `cargo <cmd> -p <crate-name>` instead of `cargo <cmd>
   --workspace`. Falls back to workspace-wide if changes span crates.
5. **Pre-commit hook**: add a pre-commit step that invokes the
   relevant `telec code` subcommand on Rust file changes, OR add
   direct cargo hook entries — match the existing pattern for Python/TS.

## Concrete acceptance criteria

When this lands:

1. A project with `languages: [python, rust]` in `teleclaude.yml`:
   - `telec code lint` runs `cargo fmt --check` and `cargo clippy
     --all-targets -- -D warnings` on the changed Rust files / crates.
   - `telec code format` runs `cargo fmt` on changed Rust files / the
     workspace.
   - `telec code test` runs `cargo test` for changed crates (or
     workspace-wide with `--all` flag).
   - `telec code commit` runs Rust lint steps in pre-commit; blocks
     commit on cargo fmt/clippy failures.
2. A project with `languages: [python]` (no rust):
   - No regression. Python pipeline unchanged.
3. A project with `languages: [rust]` (no python):
   - Pipeline invokes only cargo tooling. No Python steps run.
4. Workspace scoping correct: editing a file in `crates/workflow/src/`
   triggers `cargo test -p workflow`, not `cargo test --workspace`,
   unless `--all` is specified.
5. Pre-commit hooks for Rust pass on a clean Rust commit and fail on
   a deliberately-broken one (unformatted code, clippy warning, test
   failure).
6. Spec doc at `docs/global/general/spec/tools/telec-cli.md` updated to
   describe Rust support.

## Anti-patterns to refuse

- Hardcoding cargo paths or assuming cargo is on PATH without checking.
  Use the same tool-resolution pattern Python/TS use.
- Running `cargo` from a directory that isn't the workspace root.
  Workspace root is the `Cargo.toml` parent.
- Workspace-wide invocation when crate-scoped invocation would be
  sufficient (defeats the speed benefit of scoped pipelines).
- Adding Rust steps that fire even when `rust` isn't in the project's
  `languages` list. Pattern: language-gated invocations only.
- Coupling Rust quality work to v2 architecture decisions. This todo
  ships in v1 Python and is consumed by v2 work — the dependency is
  one-way.
- Inventing new quality tools beyond cargo's defaults unless there's
  a specific reason (existing pattern doesn't add tools beyond
  language-standard tools).

## Suggested implementation order

The prepare worker may decompose differently; this is just a sketch:

1. Read existing toolchain/lint/format/test_runner/scope modules to
   understand the language-handling pattern.
2. Add Rust registration to `toolchain.py`.
3. Add Rust steps to `lint.py` (`cargo fmt --check`, `cargo clippy`).
4. Add Rust step to `format.py` (`cargo fmt`).
5. Add Rust step to `test_runner.py` (`cargo test` with workspace
   scoping).
6. Extend `scope.py` for Rust workspace member detection.
7. Add Rust entries to `.pre-commit-config.yaml`.
8. Update spec doc.
9. Tests for each addition (Python tests of the new pipeline logic;
   integration smoke test on a sample Rust workspace).
10. Manual verification on the existing v2 `crates/` workspace
    (assumes MVP landed first; if not, create a tiny test workspace).

## Notes for the BA / orchestrator

- **Dependency on MVP:** the MVP creates the actual `crates/` workspace
  this work will be tested against. If MVP hasn't landed when this todo
  starts, the BA should either (a) defer until MVP lands, or (b) build
  a tiny mock Rust workspace in tests/ for integration testing,
  knowing the real workspace lands separately.
- **Sequence with v2 work:** ideally, this lands between MVP cutover
  and `v2-spine-completion` dispatch. That way spine-completion
  teammates can rely on `telec code` Rust support being available.
- **Scope discipline:** the BA should resist scope expansion into "let's
  also restructure the language pipeline" or "let's add Go support too."
  This todo is narrowly Rust support, mirroring the existing pattern.
