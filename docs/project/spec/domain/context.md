## What it is

The `context` bounded context owns the platform's file-based context engineering surface — the documents, skills, commands, and agent files that prime and equip agent CLIs. It validates source files against schemas, deploys derived outputs to agent runtime directories (`~/.claude/`, `~/.codex/`, `~/.gemini/`), exposes CRUD over each kind, and serves selection queries.

This context is **infrastructure-shaped, not service-shaped** in the Postgres sense — no Postgres schema, no domain events, no event-bus participation as a source. State lives in git (source under `docs/`, `agents/`, `.agents/`) and on the filesystem (deployed under `~/.<agent>/`). The crate is `crates/context/`.

The fold in v2: knowledge (docs) and agent_artifacts (skills/commands/agents) are the SAME bounded context because they share the same change axis — both are file-based, both deploy to agent runtimes, both evolve when context-engineering formats evolve. v1 split them artificially.

This context does NOT own: workflow state (`workflow`), live agent sessions (`agent_runtime`), historical session content (`session_mirrors`), durable observations (`memory`), HTTP integration (`integration`).

## Canonical fields

### Ubiquitous language

**Context**
: In the AI sense — the priming and equipping data agents receive. Encompasses both static reference (docs) and invokable capability (skills, commands, agent configs).

**Kind**
: The taxonomy of context items. Four canonical kinds:

- **doc** — documentation snippet under `docs/` following the snippet authoring schema. Static reference.
- **skill** — invocable capability deployed to agent skills directories.
- **command** — slash command (e.g., `/next-prepare`) deployed to agent command directories.
- **agent** — agent-targeting file (`AGENTS.master.md`, addenda, `AGENTS.global.md`). Behavioral configuration.

**Source**
: Authored files under git: `docs/` for docs, `agents/` for global agent items, `.agents/` for project-local agent items. Source is the truth.

**Deployed**
: Inflated/processed output written to agent runtime directories (`~/.<agent>/`). Generated by sync; never hand-edited.

**Index**
: Pre-computed catalog of docs at `~/.teleclaude/docs/index.yaml`. Built by sync. Reader entry point.

**Sync**
: The operation that validates source, inflates, and writes deployed output. Idempotent: same source → same output. Invoked by `telec context sync`.

**Selection policy**
: Pure function returning the curated context for a request (caller's role, slug, taxonomy filters, agent target). Lives in `context::selection`. Test-pinned.

**Mother project**
: This TeleClaude repo — the only repo allowed to publish global agent items from `agents/`. Other projects use `.agents/` for project-local.

**CRUD surface**
: Per-kind operations (`telec context <kind> list/get/create/update/delete`) that read source, validate against the kind's schema, and write back to git-tracked source. The foundation that lets agents author their own context (self-improvement).

<!-- planned:code-intelligence-foundation -->
**Blueprint**
: A generated structural map of the project's source — symbols (functions, classes, modules) and the dependency edges between them (calls, imports, inheritance, uses), parsed per-language. A context-engineering artifact alongside docs/skills/commands: structural code context that primes agents. Lives at `.teleclaude/blueprint/graph.json` (project root, gitignored, shared across worktrees).

**Blast-radius (affected set)**
: For an intended change to a symbol or file, the set of dependents it can affect — callers, importers, subclasses, tests — derived by reverse-traversal of the Blueprint's dependency edges. The structural input to a plan's change surface.

**Blind spot**
: A coupling the Blueprint cannot see because it is not a source-level edge — dynamic dispatch, registry/string-keyed wiring, config-driven behavior, reflection, and every cross-language boundary (Python↔Rust↔TypeScript via FFI/IPC/process). Named explicitly so the agent reads those areas manually rather than trusting an incomplete blast radius.

### Aggregates

#### ContextItem (aggregate, per kind)

- **Root:** `ContextItem<K>` where K is the kind (doc, skill, command, agent)
- **Contains:** source path; kind; scope (global | project); per-kind metadata (frontmatter for docs; invocation schema for skills; target agents for agent items); deployed paths.
- **Invariants:**
  - Source lives in git only. Files under `~/.<agent>/` are deployed output, not source — direct edits are defects overwritten by next sync.
  - Each kind has a schema; sync rejects invalid sources before deployment.
  - Global agent items publish only from the mother project; non-mother projects with files under their `agents/` fail validation.
  - Per-agent inflation may produce different outputs (Claude gets hooks; Codex/Gemini don't).
  - Idempotent: re-syncing unchanged sources produces byte-identical output.
- **Identifier:** absolute source path relative to repo root.
- **Lifecycle:** Created by hand authoring OR by agent CRUD (`telec context skills create`). Mutated by editing source or `update`. Removed by `delete` (removes source file). Deployed state refreshes on next sync.

#### Index (aggregate, doc-specific)

- **Root:** `Index`
- **Contains:** entries for every doc snippet in scope (id, type, domain, scope, description, visibility, delivered_by when applicable, source path, last-indexed timestamp).
- **Invariants:**
  - Fully derived from source files; no hand-edits ever.
  - The index is the SINGLE SOURCE OF TRUTH for classification. `id`, `type`,
    `scope`, and `domain` are derived from the snippet's path (`scope` from the
    source tree, `domain` from the id's first segment, `type` from the H1
    suffix) and materialized here — frontmatter no longer authors them, and
    consumers read these values only from the index. A path that does not
    resolve to a derivable classification FAILS the build loudly rather than
    being silently skipped.
  - Re-running sync on unchanged sources produces byte-identical index output.
  - One index per scope (global, project, third-party).
  - **Snippet validation is shape-only for lifecycle frontmatter.** Context validates `delivered_by` shape: when present it must be a non-empty list of slug strings; absence means the snippet is current. No `status` field is validated or required. Roadmap relationship state is owned by lifecycle callers, so validation does not reject unknown slugs and does not enforce delivery-lag drift.
  - **Snippet frontmatter parse/render is the shared filesystem primitive.** Context owns the canonical frontmatter primitives (`_split_frontmatter`, `_render_frontmatter`, `_iter_snippet_files`, `_delivered_by`) used by lifecycle callers. Integration uses them for delivery-time `delivered_by` reconciliation before the squash-merge commit; workflow uses them for retention-purge reconciliation and decision-time orphan refusal. Context supplies the file engine. Workflow/integration own lifecycle decisions and commit timing; the v2 docs-authority target centralizes serialized writes and exact pathspec staging inside context.

### Domain events emitted

None. Context is filesystem-driven; no event-bus participation as a source. Consumers re-read source/index when they need fresh state. The act of `git commit` + `telec context sync` is the implicit "context changed" signal.

### Domain events consumed

None. Context reads source on demand. No upstream events drive its behavior.

### Use cases

#### UC-CTX-1: Sync all kinds

```
Given source files exist under docs/ and agents/ (and optionally .agents/)
When the operator runs `telec context sync`
Then context validates every source against its kind's schema
And inflates per-agent deployed outputs
And deploys to ~/.teleclaude/docs/ (docs) and ~/.<agent>/ (skills/commands/agents)
And rebuilds the doc index
And the operation is idempotent — re-running with unchanged source produces byte-identical output
```

#### UC-CTX-2: Doc selection for a context-engineering request

```
Given a caller resolves to a Principal with a role
And the caller requests context (taxonomy filters, slug, agent target)
When context's selection policy runs
Then it filters the index by role-gated visibility, taxonomy, scope, target
And returns a curated set of snippet ids + content
And the selection is deterministic given the same inputs + same index
```

#### UC-CTX-3: Programmatic skill authoring (the self-improvement enabler)

```
Given an agent (intelligence) detects a pattern worth materializing as a skill
When the agent runs `telec context skills create --name <slug> --content <yaml>`
Then context validates the content against the skill schema
And writes the source file to agents/skills/<slug>.md (global) or .agents/skills/ (project-local)
And the next sync deploys it to the agent runtime directories
```

#### UC-CTX-4: Agent file update (e.g., addendum revision)

```
Given an operator (or agent) wants to revise the Claude addendum
When they run `telec context agents update CLAUDE.addendum.md <content>`
Then context validates the addendum schema
And writes the source file
And next sync re-inflates AGENTS.master.md with the new addendum content
```

#### UC-CTX-5: Reject unauthorized global publishing

```
Given a non-mother project has files under its agents/ directory
When `telec context sync` runs in that project's context
Then context rejects the operation with an error naming the violated rule
And directs the operator to .agents/ for project-local items
```

#### UC-CTX-6: Three-phase doc retrieval

```
Given an agent needs context
When the agent runs `telec context docs list --area policy --domain software-development`
Then context returns snippet metadata for matching snippets, with " (delivered by: …)" suffix for pending entries
When the agent runs `telec context docs get <id> [<id>...]`
Then context returns the full snippet content for those ids, with any cross-snippet "Required reads (not loaded)" listed for explicit follow-up fetch
```

### Self-improvement / mining (consumer pattern)

The CRUD surface enables agents to author their own context. The mining workers themselves live OUTSIDE this context — they're intelligence (agent workers) that:

1. Subscribe to `agent_runtime.extract-window` for live session data (see `agent_runtime` domain spec)
2. Detect patterns (skill candidates from repetition; memory candidates from observations)
3. Write via the CRUD surfaces (`telec context skills create` for skills; `telec memory save` for observations)

No mining service exists. No event subscription in context. Pattern detection is intelligence + shared utilities + CLI bridges. See `transport-rules.md` "Cross-cutting concerns via intelligence + shared utilities + CLI" for the pattern.

### Codebase blueprint (structural code intelligence)

`context` owns the project's **Blueprint** — a generated structural map of the source that agents (at plan time especially) consult to obtain the blast radius of an intended change instead of grepping. The engine is the Graphify CLI, adopted as-is behind the `graph.json` data-contract seam (see `project/adr/0016-graphify-as-codebase-blueprint-engine`).

- **Languages:** Python, Rust, TypeScript — one graph spanning all three. Python and Rust are high-fidelity; TypeScript extracts and queries but yields a sparser dependency graph (React/JSX), so its blast-radius is less complete — validate per use.
- **Generation (automation, never agents):** the integrator regenerates the baseline on a successful remote-main pull, writing `.teleclaude/blueprint/graph.json` at the project root (gitignored, shared across worktrees like `todos.db`). Worktrees read that baseline; there is no per-step drift handling — a worktree is stable against the baseline it branched from, and the next integrate refreshes code and Blueprint together. Pinned and installed via `make install`.
- **Agent how-to (consumption):** the blast-radius discipline lives in the `plan-draft` procedure. Concrete commands: `graphify query "<terms>"` to surface seed symbols; the **blast-radius helper** (`changed-files → symbol node-ids → affected → union`, reading `graph.json`) to get the dependent set — the helper exists because `graphify affected` resolves only unique symbol seeds and Graphify has no file→dependents primitive of its own. Pair with `graphify path` for reachability.
- **Fallback:** if the Blueprint is missing or stale, the area is unsupported, or a Blind spot applies, the agent states the gap and falls back to manual exploration — blast-radius is never silently skipped.

This subsection is the concrete "codebase-intelligence documentation" the plan-draft discipline references.

### Context map position

- **Customer-Supplier downstream of `identity`** — selection policy uses caller's role to gate visibility.
- **Customer-Supplier downstream of `config`** — reads per-project doc roots, taxonomy defaults, sync targets.
- **Customer-Supplier upstream to every domain context** — every context consumes context (docs at minimum; skills/commands per-agent).
- **Open Host Service to any caller** — index/get/select interface is a stable read surface.
- **Conformist via filesystem from `agent_runtime`** — context deploys hook configs that `agent_runtime`'s `telec-hook` binary reads. The handshake is filesystem-mediated.
- **Anti-corruption layer with v1 (during migration)** — v1 `teleclaude/docs_index.py` + `context_selector.py` + `sync.py` + `install/configure_agent_cli.py`. The v2 shim preserves public function signatures; actual logic moves to `crates/context/`. NO separate cutover todo — v1 and v2 read the same source files; they can coexist forever.

## Allowed values

- `kind`: `doc`, `skill`, `command`, `agent`.
- `scope`: `global` (publishable only from mother project), `project` (any project, under `.agents/` / project's `docs/`).
- `target agent`: `claude`, `codex`, `gemini` (extensible).

## Known caveats

- **Filesystem-driven, no Postgres schema, no events.** State lives in git + filesystem. Adding a database would be overhead with no payoff; the index file IS the index.
- **`telec context sync` is the deployment boundary.** No partial writes; consumers read from deployed locations, never from working-tree source. Sync at commit boundary keeps deployed == committed.
- **Mother-project gate** prevents accidental global publishing from non-mother repos.
- **CRUD writes to source (git-tracked).** Agent self-improvement = agent authors a skill → file lands in git → sync deploys → next agent session has the new skill. Loop closed via git + sync, not via any in-memory state.
- **No cutover follow-up.** v1 (`teleclaude/docs_index.py` + `context_selector.py` + `sync.py`) and v2 (`crates/context/`) read the same source files. They can coexist forever. The v1 Python paths can retire when convenient (or never).
- **Hooks frontmatter is Claude-only in deployed output.** Inflation strips hooks for non-Claude targets.
- **No new kinds without schema update.** The four kinds are deliberate.
- **Generated indexes (`docs/index.yaml`, AGENTS.md baseline blocks) are toolchain outputs.** Per `Commits` policy: sync is the only writer; they ARE committed because consumers depend on them.
