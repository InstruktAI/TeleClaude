# MCP Registry Resolution — Design

## Purpose

Resolve one effective MCP catalog per invocation context so a project's own registry declarations serve that project's sessions through the standard `telec mcp` surface, while every other context keeps the machine-wide catalog. The behavioral contract lives in `project/spec/feature/agent_runtime/lazy-mcp-runtime`; the registry file and schema contract lives in `project/spec/teleclaude-config`; this design fixes the technical shape that realizes both.

### Prior art & adopt-vs-build

- **Path-authority validation — adopted from platform precedent.** The canonical genuine-checkout resolution (`resolve_project_root` / `is_project_checkout`, the `teleclaude.yml` marker) is the platform's existing authority pattern for "is this directory a TeleClaude project"; this design consumes that contract plus canonical registry-file presence rather than inventing a path allowlist. The alternative — trusting caller-supplied paths with ad-hoc checks — is rejected as an open filesystem-authority boundary.
- **Runtime pooling — adapted from the runtime's own lease pattern.** The daemon already runs a keyed pool with idle reaping one level down (slug-keyed MCP leases inside one runtime); the design extends the same shape one level up (root-keyed runtimes inside one manager), reusing the established reaper/shutdown traversal discipline visible in the daemon's existing session and lease lifecycle code. A per-project daemon process — the comparable isolation alternative — is rejected as incompatible with the single-daemon platform design and its shared identity/transport stack.
- **Scoped-config authority — consistent with vendor practice.** The consolidated third-party research for the supported agent CLIs (per-CLI `mcp-config` docs) documents the same model this design adopts: project-scoped MCP configuration gated by an explicit trust/registration boundary (Claude Code folder trust, Codex trusted projects). No external infrastructure is introduced; adopt-vs-build resolves to build-nothing-new — compose three existing platform mechanisms.

## Inputs/Outputs

- **Inputs:** the machine-wide registry files at the TeleClaude repository root; a project's `teleclaude-mcp.jsonc` / `teleclaude-mcp.local.jsonc` at its checkout root; the invocation working directory; the caller identity already verified on `/mcp` routes.
- **Outputs:** the effective per-scope catalog served by `telec mcp list` and the `/mcp` routes; per-root daemon runtimes with isolated leases, tool-catalog caches, and fingerprints; baked MCP index sections in generated agent entrypoint files.

## Invariants

- **One resolver owns layering** (`@prd#sc-2-precedence-is-observable-within-the-project`). Complete machine-plus-project resolution lives behind a single config-owned API — `load_effective_registry(project_root: Path | None)` — consumed identically by CLI discovery and the daemon. No caller composes layers itself. Layering inside the resolver is fixed: machine-wide shared → machine-wide local → project shared → project local, deep-merged by the existing merge semantics.
- **The project layer reads canonical files only.** `mcp.json` / `mcp.local.json` compatibility imports remain a machine-wide-root contract; for a project root the resolver reads exactly `teleclaude-mcp.jsonc` and `teleclaude-mcp.local.jsonc`. This is a recorded divergence from the reuse-the-loader hypothesis in the filed input: the current per-root loader consults compatibility inputs for any root it is given, which would admit unauthorized project input shapes.
- **Project context travels only when a project registry exists** (`@prd#sc-9-everything-else-is-unchanged`). The single emission condition, identical wherever context is produced: the CLI supplies project context on a request if and only if the resolved invocation root declares a project registry (a canonical registry file present at the root). A checkout with no registry files sends no context and is served machine-wide exactly as today. A supplied root is validated fail-fast as a genuine TeleClaude checkout — canonicalized, `teleclaude.yml` marker present, registry file present (`@prd#premises-and-assumptions`); anything else is rejected with a caller-safe error, never silently downgraded to machine-wide authority.
- **One runtime per validated root, one pool owner** (`@prd#sc-5-concurrent-contexts-stay-isolated`). A runtime manager owned by the daemon holds root→runtime state: runtimes are created lazily on first validated use, the reaper traverses every runtime's leases, and daemon shutdown closes every lease of every runtime. A lease, cached tool catalog, or fingerprint never serves another root. The machine-wide runtime is the pool's permanent default entry.
- Environment placeholders resolve daemon-side at lease start (`@prd#sc-6-credential-behavior-is-inherited-secret-safe-per-root`) from the TeleClaude environment, identically for both scopes; no secret enters a file or an agent session.
- `hidden: true` on a server entry affects only baked-index rendering (`@prd#sc-8b-index-visibility-is-a-per-declaration-choice`); runtime `telec mcp list`, tool listing, calls, launch, and fingerprints are unaffected. Project declarations never produce writes to user-home native agent configs; no publication path exists.

## Primary flows

- **CLI discovery (`telec mcp list`):** resolve the invocation project root via the existing invocation-position normalization (subdirectories and todo worktrees resolve to the owning checkout) and call the config-owned resolver with it. In-process resolution here is the standing live contract, anchored by the existing UC-LMCP-14 (listing succeeds while the daemon is down) — the recorded exception to API-mediated CLI reads, consumed strictly through the resolver's published contract. Outside any project checkout, resolution fails exactly as it does today. API consumers get the identical catalog through the existing `GET /mcp/servers`, which serves the same typed scope.
- **Project context on the API** (`@prd#sc-3-tool-listing-and-calls-honor-the-project-effective-catalog`): `tool_api_call` — the seam that already injects identity headers — adds `x-teleclaude-project-root` under the single emission condition above. The validity rule — what constitutes acceptable project context — is owned by the `context` bounded context and published as a typed project-context contract; daemon-side, a route dependency beside `verify_caller` is the injection-layer consumer of that contract, translating the header (canonical genuine-checkout with a project registry) into the typed scope — the validated root, or machine-wide when the header is absent. Validation failure maps to a 400 with a caller-safe `invalid_project_context` error naming no filesystem detail. The `/mcp` routes consume only the typed scope and select the runtime from the pool with it.
- **Config drift:** the existing per-runtime fingerprint and drift rules apply within each root; a changed project registry invalidates only that root's leases.
- **Baked indexes ride the existing distribution paradigm** (`@prd#sc-1-project-servers-are-contained-to-their-project`, `@prd#sc-8-the-projects-agent-entrypoint-carries-its-mcp-index`). Baked-index policy is owned by the `context` bounded context — the owner of agent-asset publication — with distribution as its rendering and deployment layer. The rendering primitive is one internal directive, `@mcp-index`, expanded by the same distribution machinery that expands `@exec`: it renders from the resolver directly with the scope fixed by the artifact being generated — machine-wide declarations for globally deployed artifacts, the project's own declarations for a project's entrypoint — always excluding `hidden` entries. The global procedure's baked list switches from `@exec: telec mcp list` to `@mcp-index` (carried as a pending change on that procedure), because the runtime listing by contract shows hidden servers and is project-effective, so it can no longer serve any baked index. No new public CLI surface exists; the runtime `telec mcp list` is unchanged. A project with no declarations renders no section; scope is fixed by the generating artifact, so no distribution run can leak one scope's entries into another's output.
- **Schema:** the registry JSON schema gains the optional boolean `hidden` (default `false`) on server entries; both scopes use the identical schema. The config-owned contract for project registry files and `hidden` is carried as a pending change on `project/spec/teleclaude-config`.

## Failure modes

- **Supplied project root failing genuine-checkout or registry-presence validation:** the request fails with the caller-safe `invalid_project_context` error; nothing is read from the offered path. The rejection is logged with the stable reason and the authenticated caller and correlation identifiers — never the offered filesystem path.
- **Project registry parse or contract error:** the existing registry error path fails the request naming the offending file and server; the machine-wide runtime is unaffected.
