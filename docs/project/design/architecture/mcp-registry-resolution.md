# MCP Registry Resolution — Design

## Purpose

Resolve one effective MCP catalog per invocation context so a project's own registry declarations serve that project's sessions through the standard `telec mcp` surface, while every other context keeps the machine-wide catalog. The behavioral contract lives in `project/spec/feature/agent_runtime/lazy-mcp-runtime`; the registry file and schema contract lives in `project/spec/teleclaude-config`; this design fixes the technical shape that realizes both.

### Prior art & adopt-vs-build

- **Path-authority validation — adopted from platform precedent.** The canonical genuine-checkout resolution (`resolve_project_root` / `is_project_checkout`, the `teleclaude.yml` marker) is the platform's existing authority pattern for "is this directory a TeleClaude project"; this design consumes that contract plus canonical registry-file presence rather than inventing a path allowlist. The alternative — trusting caller-supplied paths with ad-hoc checks — is rejected as an open filesystem-authority boundary.
- **Runtime pooling — adapted from the runtime's own lease pattern.** The daemon already runs a keyed pool with idle reaping one level down (slug-keyed MCP leases inside one runtime); the design extends the same shape one level up (root-keyed runtimes inside one manager), reusing the established reaper/shutdown traversal discipline visible in the daemon's existing session and lease lifecycle code. A per-project daemon process — the comparable isolation alternative — is rejected as incompatible with the single-daemon platform design and its shared identity/transport stack.
- **Scoped-config authority — comparable vendor examples, own boundary.** Per the consolidated per-CLI research: Claude Code gates project MCP config behind folder trust plus per-server approval, and Codex behind project trust — comparable precedents for trust-gated project scope. Antigravity's workspace-load trust is unestablished in vendor docs, and DeepSeek dsh has no auto-discovered project MCP layer (only an explicit `--patch` mechanism), so no universal vendor model exists. TeleClaude grounds its boundary in its own contracts instead: authenticated caller identity and the canonical genuine-checkout resolution. No external infrastructure is introduced; adopt-vs-build resolves to build-nothing-new.

## Inputs/Outputs

- **Inputs:** the machine-wide registry files at the TeleClaude repository root; a project's `teleclaude-mcp.jsonc` / `teleclaude-mcp.local.jsonc` at its checkout root; the invocation working directory; the caller identity already verified on `/mcp` routes.
- **Outputs:** the effective per-scope catalog served by `telec mcp list` and the `/mcp` routes; per-root daemon runtimes with isolated leases, tool-catalog caches, and fingerprints; baked MCP index sections in generated agent entrypoint files.

## Invariants

- **One resolver owns layering** (`@prd#sc-2-precedence-is-observable-within-the-project`). Complete machine-plus-project resolution lives behind a single config-owned API — `load_effective_registry(project_root: Path | None)`. No consumer composes layers itself. Layering inside the resolver is fixed: machine-wide shared → machine-wide local → project shared → project local, deep-merged by the existing merge semantics. The TeleClaude Mother root is the canonical machine-wide scope: the resolver treats it as machine-wide with no project overlay, and the pool maps it to the permanent machine-wide runtime — the same files are never merged twice and machine definitions never get a duplicate lease pool.
- **The project layer reads canonical files only.** For a project root the resolver reads exactly `teleclaude-mcp.jsonc` and `teleclaude-mcp.local.jsonc`; `mcp.json` / `mcp.local.json` compatibility imports are a machine-wide-root contract and are never read from a project root.
- **MCP scope is derived per caller class; a session request never selects it** (`@prd#sc-1-project-servers-are-contained-to-their-project`, `@prd#sc-3-tool-listing-and-calls-honor-the-project-effective-catalog`). Two caller classes exist on the verified-caller contract:
  - **Session callers** (agent sessions): scope is derived server-side from the session's own recorded project — published on the verified-caller contract, populated at caller verification by its owner. No request header, parameter, or body field selects or overrides it, so cross-project forgery has no carrier.
  - **Sessionless human-verified callers** (terminal and TUI identities with no agent session): the CLI supplies its invocation-normalized project root with the request; the daemon serves that scope after validating it as a canonical genuine TeleClaude checkout with a project registry present. This class carries the human trust class of the machine owner; a validation failure is rejected caller-safe, never downgraded.
  - In both classes, a project root that declares no registry yields machine-wide scope; outside every TeleClaude project the existing behavior is unchanged (`@prd#sc-9-everything-else-is-unchanged`).
- **The session→project fact crosses on a published contract.** `agent_runtime` owns the fact; it reaches `/mcp` routes exclusively through the verified-caller contract (a typed project field on the caller identity populated during caller verification). Routes never read session persistence directly.
- **One runtime per resolved root, one pool owner** (`@prd#sc-5-concurrent-contexts-stay-isolated`). A runtime manager owned by the daemon holds root→runtime state: runtimes are created lazily on first use, the reaper traverses every runtime's leases, and daemon shutdown closes every lease of every runtime. A lease, cached tool catalog, or fingerprint never serves another root. The machine-wide runtime is the pool's permanent default entry.
- Environment placeholders resolve daemon-side at lease start (`@prd#sc-6-credential-behavior-is-inherited-secret-safe-per-root`) from the TeleClaude environment, identically for both scopes; no secret enters a file or an agent session.
- `hidden: true` on a server entry affects only baked-index rendering (`@prd#sc-8b-index-visibility-is-a-per-declaration-choice`); runtime `telec mcp list`, tool listing, calls, launch, and fingerprints are unaffected. Project declarations never produce writes to user-home native agent configs; no publication path exists.

## Primary flows

- **CLI discovery (`telec mcp list`):** `presentation` owns the CLI surface and consumes the config-owned resolver contract with the invocation-normalized root (`@prd#sc-4-worktrees-behave-as-their-owning-project`) — the same client-side configuration seam through which the CLI reads every other TeleClaude configuration contract, which is what keeps discovery available while the daemon is down (the live UC-LMCP-14 contract). Outside any project checkout, resolution fails exactly as it does today. API consumers get the identical catalog through the existing `GET /mcp/servers`, which serves the caller-derived scope.
- **Scope on the API:** a route dependency beside `verify_caller` produces the typed scope from the verified-caller contract per the caller-class invariant above. The `/mcp` routes consume only the typed scope and select the runtime from the pool with it.
- **Config drift:** the existing per-runtime fingerprint and drift rules apply within each root; a changed project registry invalidates only that root's leases.
- **Baked indexes ride the existing distribution paradigm** (`@prd#sc-1-project-servers-are-contained-to-their-project`, `@prd#sc-8-the-projects-agent-entrypoint-carries-its-mcp-index`). Baked-index policy is owned by the `context` bounded context — the owner of agent-asset publication — with distribution as its rendering and deployment layer. The rendering primitive is one internal directive, `@mcp-index`, expanded by the same distribution machinery that expands `@exec`: it renders from the resolver directly with the scope fixed by the artifact being generated — machine-wide declarations for globally deployed artifacts, the project's own declarations for a project's entrypoint — always excluding `hidden` entries. The global procedure's baked list uses `@mcp-index` (carried as a pending change on that procedure); the runtime listing shows hidden servers and is project-effective, so it serves no baked index. No new public CLI surface exists; the runtime `telec mcp list` is unchanged. A project with no declarations renders no section; scope is fixed by the generating artifact, so no distribution run can leak one scope's entries into another's output.
- **Schema:** the registry JSON schema carries the optional boolean `hidden` (default `false`) on server entries; both scopes use the identical schema. The config-owned contract for project registry files and `hidden` is carried as a pending change on `project/spec/teleclaude-config`.

## Failure modes

- **A session's recorded project exists and declares no registry:** valid state — the session is served machine-wide by contract.
- **A session's recorded project cannot be resolved or validated:** failed scope resolution — the request is rejected with a caller-safe `project_scope_unresolved` error; the condition is logged with the stable reason and the session identifier, never a filesystem path.
- **A sessionless caller's supplied root fails genuine-checkout or registry validation:** the request is rejected with a caller-safe `invalid_project_context` error; nothing is read from the offered path; the rejection is logged path-free with the stable reason and caller identifiers.
- **Project registry parse or contract error:** the existing registry error path fails the request naming the offending file and server; the machine-wide runtime is unaffected.
